## 1. Sweep grammar — what expands into an axis

`parse_value` (`sweep_parser.py:40`) is the whole grammar. Detection order is: bracket-delimited list → boolean → `float()` → `float(Fraction())` → bare string.

List detection is **purely by first and last character** (`sweep_parser.py:71`): `if val_str.startswith('[') and val_str.endswith(']')`. There is no tokenizer. `parse_list` (`sweep_parser.py:96`) then does `items = [item.strip() for item in inner.split(',')]` (`:123`) — a naive split on every comma at every depth, with no quote or bracket awareness. Consequences, all silent:

- `mCloud [[1e5,1e6],[1e7,1e8]]` yields the four **strings** `'[1'`, `'2]'`… (verified: `'[[1,2],[3,4]]'` → `['[1','2]','[3','4]']`). No error; a 4-point axis of nonsense strings.
- `label ["a, b", "c"]` yields `['"a', 'b"', '"c"']` — three axis points, quote characters retained. Nothing in the file strips quotes, so a quoted scalar `dens_profile "densPL"` becomes the literal string `"densPL"`, which fails the `== 'densPL'` test at `sweep_parser.py:739` and the membership test at `sweep_runner.py:100`.
- A trailing comma, `sfe [0.01, 0.10, ]`, yields a **third axis point that is the empty string** — `''` fails `float()`, fails `Fraction()`, and is appended verbatim at `sweep_parser.py:145`. The sweep silently gains a bogus combination.

The two `except (ValueError, ZeroDivisionError)` fallthroughs (`:139-145` in lists, `:226-229` in tuples, `:89-90` for scalars) mean **any typo in a numeric list silently becomes a string sweep value**: `mCloud [1e5, 1e7, 1e8x]` is a legal 3-point sweep whose third run gets `mCloud    1e8x`. `1/0` is caught by `ZeroDivisionError` and degrades to the string `'1/0'`.

`float()` also accepts `nan`, `inf`, `-Infinity`, and underscore-separated digits. A swept `nan` reaches `format_scientific`, where `value == int(value)` (`:826`) raises `ValueError: cannot convert float NaN to integer`; `inf` reaches `math.floor(math.log10(inf))` at `:811` and raises `OverflowError`. Neither produces a message naming the offending parameter.

Comment stripping is `if '#' in line: line = line[:line.find('#')]` (`:310-311`, `:408-409`) — unconditional, at any column, with no escape or quoting mechanism, so a value containing `#` is silently truncated.

Single-element lists are **demoted to base params**, not treated as a 1-point axis (`:338-341`, `:451-453`), identically in both readers. A consequence worth noting: because the key never enters `sweep_params`, it is never in the `swept_keys` passed to `generate_run_name`, so its value does not appear in the run name — `Z [0.5]` and `Z 0.5` produce identical output directories. Empty lists raise (`:334-337`).

Tuple mode (`parse_tuple_line`, `:154`) is recognised by `line.lower().startswith('tuple(')` and uses `line.find('(')` / `line.find(')')` (first occurrence only, `:184-185`) plus the regex `r'\[([^\]]+)\]'` (`:202`). Value-count mismatch raises (`:210-214`), which is good, but `[^\]]+` requires at least one character, so an empty bracket group is **silently skipped**: `tuple(a, b)  [1, 2] [] [3, 4]` produces two combinations, not an error. Duplicate names inside `tuple(a, a)` are not detected; `zip` at `:517`/`:534` simply lets the last win.

Neither reader detects **duplicate keys**. Two scalar lines for the same key: last wins silently. A scalar line *and* a list line for the same key: both dicts retain an entry, and because `generate_combinations` does `params = base_params.copy()` then overwrites from the sweep (`:576-578`), the sweep silently wins regardless of file order. A stale line left above an edited one is never reported.

## 2. Combination generation, naming, and collisions

Order is `itertools.product(*value_lists)` over `keys = list(sweep_params.keys())` (`:570-574`) — i.e. **file line order**, last key varying fastest. Deterministic and reproducible for a fixed file. Note the asymmetry: the combination *index* (and therefore the `runs.tsv` line number an array task reads) depends on line order, while the run *name* does not, because generic suffixes iterate `sorted(swept_keys)` (`:761`). Reordering two lines in a `.param` renumbers every job but renames none.

Copying is clean: `base_params.copy()` per combination (`:576`), `tuple_base.copy()` per tuple then `tuple_base.copy()` per sweep point in hybrid mode (`:516`, `:525`). No shared-dict mutation across combinations. `count_combinations_from_config` (`:855`) matches the generator's cardinality in all three modes.

**The naming function is where this slice breaks.** `generate_run_name` (`:683`) builds `f"{mcloud_str}_sfe{sfe_str}_n{ncore_str}"` plus profile and PHII tokens, then appends generic `key+value` tokens **only for swept keys not in `_NAMED_RUN_NAME_KEYS`** (`:762`):

```
761	        for key in sorted(swept_keys):
762	            if key in _NAMED_RUN_NAME_KEYS or key not in params:
763	                continue
```

`_NAMED_RUN_NAME_KEYS` (`:590`) contains `mCloud, sfe, nCore, dens_profile, densPL_alpha, densBE_Omega, include_PHII`. For those seven keys the *only* disambiguation is the lossy base-name encoding, and there is **no fallback** if that encoding loses information. It does, in four independent ways:

- `densPL_alpha` is rendered `int(alpha)` — **truncation toward zero, not rounding** (`:742`). Sweeping `densPL_alpha [-2.0, -1.5, -1.0, -0.5, 0.0]` produces `_PL-2, _PL-1, _PL-1, _PL0, _PL0` — 3 distinct names for 5 combinations.
- `sfe` is rendered as an integer percentage, `int(round(sfe*100))` formatted `:03d` (`:728-729`). Any grid finer than 1% collapses: `sfe [0.010, 0.012, 0.014]` → `sfe001` three times.
- `mCloud`/`nCore` go through `format_scientific`, whose non-integer-mantissa branch is `f"{mantissa:.2g}e{exp}"` (`:823`) — **two significant figures**. `mCloud [1.23e6, 1.24e6, 1.25e6]` → `1.2e6` three times.
- `densBE_Omega` is `int(round(omega))` (`:747`): `[14.1, 14.4, 14.8]` → `_BE14, _BE14, _BE15`.

A fifth path: if `dens_profile` is swept to any value that is neither `'densPL'` nor `'densBE'`, the `if/elif` at `:739-748` adds nothing, and the generic-suffix escape hatch is closed because `dens_profile ∈ _NAMED_RUN_NAME_KEYS`. Every such combination gets the identical name.

The truncate-vs-round asymmetry between alpha (`int`) and Omega (`int(round(...))`) is itself an internal inconsistency: two adjacent branches of the same `if`, four lines apart, disagree on how to reduce a float to an integer token.

**Nothing anywhere checks for duplicate names.** `emit_jobs` materialises the full list at `sweep_jobs.py:129` — the one place a collision check would be free — and then writes, per combination:

```
176	        out_dir = os.path.join(base_output_dir, name)
177	        param_path = params_dir / f"{name}.param"
178	        param_path.write_text(
179	            generate_param_file(params, name, out_dir), encoding='utf-8'
180	        )
```

so the later combination's `.param` overwrites the earlier one's, `runs.tsv` gains two identical lines, and two array tasks run the *same* configuration into the *same* `$OUTDIR`. The manifest still lists both with their distinct `params` dicts, `n_jobs` still counts both, and `collect_report` reads the same sentinel twice and reports two successes. The user is told N runs succeeded when fewer than N distinct configurations were ever executed. The in-process path has the same shape — `output_dir.mkdir(parents=True, exist_ok=True)` (`sweep_runner.py:247`) then a same-named `.param` write (`:252-256`) — and if the out-of-slice driver runs colliding combinations concurrently, two workers write the same param file while a third reads it.

The generic-token path has a milder collision of its own: `_SAFE_VALUE_CHARS_RE = re.compile(r'[^A-Za-z0-9.+\-]')` (`:606`) maps every unsafe character to `-` (`:677`), so string sweep values `a b`, `a_b`, `a*b`, `a?b` all become the token `a-b`.

The safety rails that *do* exist are good and worth recording: `_reject_unsafe_sweep_value` (`:609`) hard-rejects `..`, `/`, `\`, and control characters in string sweep values with an explanatory message, and `_MAX_RUN_NAME_LEN = 200` (`:599`) raises a well-worded error naming the contributing keys (`:766-775`). Both fire during `generate_combinations_from_config`, so both are exercised by `--dry-run`.

## 3. Job emission

`emit_jobs` (`sweep_jobs.py:98`) resolves `jobs_dir` and `base_output_dir` to absolute paths (`:126-127`) but **not** `trinity_root`, which is interpolated raw into the sbatch as `run_py=Path(trinity_root) / 'run.py'` (`:218`). Two of three path inputs are normalised; the third is trusted. Whether that matters depends on what `run.py` passes (out of slice).

The emitted script is `_SBATCH_TEMPLATE` (`:52-95`). Quoting is mostly right — `sed -n "${N}p" "{runs_tsv}"` (`:81`) and `python "{run_py}" "$PARAM"` (`:90`) are quoted, `mkdir -p "$OUTDIR"` is quoted, and the job name is sanitised to `[A-Za-z0-9_.-]`, truncated to 60, with an `or "sweep"` fallback (`:207-209`). The exception is line 62:

```
62	#SBATCH --output={logs_dir}/%A_%a.out
```

unquoted, and `#SBATCH` directives are whitespace-split by SLURM, so a jobs directory containing a space produces a malformed directive. Similarly `runs.tsv` is written as `f"{param_path}\t{out_dir}"` (`:188`) and parsed by `cut -f1`/`cut -f2` (`:86-87`), which is tab-fragile if `base_output_dir` ever contains a tab (run names cannot, since control characters are rejected for strings and numeric tokens are safe).

Environment assumptions baked into the emitted script: bwForCluster-specific `--partition=cpu-single`, `--account=bw22J006`, `--mem=1024M`, `--time=1:15:00`; `module load devel/miniforge` and `conda activate trinity`; `--export=NONE` with a login shell. The script never `cd`s, so `run.py` executes with the submission directory as cwd.

The overwrite guard checks only the manifest:

```
160	    manifest_path = jobs_dir / MANIFEST_NAME
161	    if manifest_path.exists():
162	        sys.exit(...)
```

`params/`, `logs/` and `runs.tsv` are then written unconditionally (`:168-192`), so an emit that died after `runs.tsv` but before the manifest leaves stale `.param` files that a re-emit into the same directory silently keeps alongside the new ones. There is also no guard on `n_jobs` against a cluster's `MaxArraySize` — the template's own embedded note points at OFFSET-chunking as the manual workaround.

Both error exits use `sys.exit(str)` (`:132`, `:162`, `:293`), which prints to stderr and exits 1 — fine for CLI use, but it makes `emit_jobs`/`collect_report` unusable as library calls and untestable without `pytest.raises(SystemExit)`.

## 4. Worker execution

**The parallel driver is not in this slice.** These three files contain no pool, no thread, no `concurrent.futures`; `run_single_simulation` (`sweep_runner.py:212`) has zero in-slice callers. Everything about how many workers run, how their results are aggregated, and what process exit code the CLI returns lives in `run.py`, which I did not read. What I can say about the single-run primitive:

Each combination runs as `subprocess.run([sys.executable, run.py, param_path], cwd=trinity_root, capture_output=True, timeout=…)` (`:285-292`). Because it is a fresh interpreter per combination, **trinity's module-level global state cannot leak between combinations** — the isolation property CLAUDE.md cares about holds here.

Failures never raise; they are converted to `SimulationResult(success=False)` with the last 2000 characters of stderr (`:307-319`). `return_code=-1` is used for three distinct conditions — param-file write failure (`:261`), timeout (`:327`), and any other exception (`:338`) — and separately means "unreadable sentinel" in `sweep_jobs.collect_report` (`:321`, and the `rc_note` map at `:267`). Whether a failing sweep produces a non-zero process exit is out of slice.

Two divergences between the local runner and the emitted sbatch, on the same contract:

- Thread caps. Local uses `sim_env.setdefault('OMP_NUM_THREADS', '1')` (`:277-281`), which is a **no-op if the user already exported `OMP_NUM_THREADS=8`** — so N workers × 8 threads oversubscribe. The sbatch uses unconditional `export OMP_NUM_THREADS=1` (`sweep_jobs.py:71-74`).
- Wall-clock budget. Local defaults to `timeout_hours: float = 24.0` (`:217`); the sbatch hard-codes `#SBATCH --time=1:15:00` (`sweep_jobs.py:61`). A sweep validated locally under a 24 h ceiling is submitted under a 75-minute one.
- cwd. Local sets `cwd=str(trinity_root)` (`:287`); the sbatch never `cd`s. If anything downstream of `run.py` resolves a relative path (bundled `lib/default/` tables are the obvious candidate), the two paths behave differently. I cannot confirm the dependency from inside the slice.

`subprocess.run(timeout=…)` kills the direct child only; no process group is created, so grandchildren survive a timeout. `capture_output=True` buffers the entire stdout/stderr in memory although only the last 2000/500 bytes are ever used.

## 5. `--dry-run` fidelity

The dry-run path is faithful about *what* would be emitted: it builds the real combination list (`sweep_jobs.py:129`), so name-length and unsafe-value rejections fire identically, runs the same validation loop (`:138-143`), and reports the same `1-{n}{throttle}` array spec the template would receive (`:150` vs `:58` + `:145`).

It diverges in one way: it returns at `:155`, **before** the manifest-exists guard at `:161`. Pointed at a directory that already holds a bundle, `--dry-run` prints "Would emit N job(s)" and the real invocation then aborts with "Refusing to overwrite a job bundle". Dry-run also cannot surface name collisions, because nothing detects them.

The validation swallow deserves emphasis because of how its result is consumed:

```
sweep_jobs.py:140	        result = _validate_sweep_combination(params)
sweep_jobs.py:141	        if result is not None and not result.valid:
```

`None` means "valid" here. `_validate_sweep_combination` returns `None` for an unrecognised `dens_profile`, for missing `mCloud`/`nCore`/`alpha`/`Omega`, and — via `except Exception: return None` at `:147-148` — for *any* failure inside the validator. So `emit_jobs` prints no warning both when every combination is plausible and when not a single one was actually checked, and the message it does print ("`{n_invalid}/{n_jobs} combos have implausible GMC parameters`") implies a denominator of checked combinations that it never computes.

`_validate_sweep_combination` also re-declares schema defaults locally: `mu_convert` → `1.4` (`:116`), `nISM` → `1.0` (`:117`), `rCloud_max` → `R_CLOUD_MAX` (`:127`), `gamma_adia` → `5.0/3.0` (`:143`). If any of these differs from the `.param` schema default (which lives out of slice in `trinity/_input/`), the plausibility check silently validates a configuration that is not the one that will run.

`generate_run_name` does the same thing with more visible consequences: `params.get('mCloud', 1e6)`, `params.get('sfe', 0.01)`, `params.get('nCore', 1e5)` (`:720-722`), `params.get('densPL_alpha', 0)` (`:740`), `params.get('densBE_Omega', 14.1)` (`:745`). A `.param` that omits `mCloud` yields a directory named `1e6_…` while the simulation runs whatever the schema default is. The name is an assertion about the physics that the naming code is not entitled to make.

## 7. Value fidelity through `generate_param_file`

`generate_param_file` (`sweep_runner.py:155`) is the bridge from an in-memory combination back to a `.param`:

```
196	            if abs(value) >= 1e4 or (abs(value) < 0.01 and value != 0):
197	                val_str = f"{value:.6g}"
```

`%.6g` is **six significant figures**, so a swept value outside the mid-range is silently rounded before the simulation ever sees it: `1234567.0` → `'1.23457e+06'` → reparsed `1234570.0`; `12345.6789` → `'12345.7'`; `0.001234567` → `'0.00123457'`. The run *name* is computed from the full-precision value but the run *executes* the rounded one. Mid-range floats use `str(value)` (`:199`), which is round-trip exact, so the loss is confined to the extremes — which is exactly where GMC masses and densities live.

Adjacent hazards in the same function: a string value that is empty (reachable via the trailing-comma path in §1) emits `f"{key}    "`, and re-reading that line hits `len(parts) != 2` and raises. A string value containing `#` is truncated on re-read. Booleans round-trip correctly (`str(True)` → `'True'` → `parse_value` → `True`).

## 8. Reporting and collection

`collect_report` (`sweep_jobs.py:282`) reconstructs a `SweepReport` from the manifest plus per-run sentinels. Two things it asserts that it does not know:

- `start_time = datetime.fromisoformat(manifest['generated'])` (`:300`) is the **emission** timestamp, not any run's start. `write_report` then prints it as `Start time:` and prints `Duration: {end - start}` (`sweep_runner.py:489-492`). For an HPC bundle submitted Monday and collected Friday, the reported sweep duration is four days of wall clock, most of it queue and idle time.
- `run_single_simulation` never writes `.exit_code` or `.duration`; only the emitted sbatch does (`sweep_jobs.py:92-93`). The sentinel contract is therefore emit-path-only. In practice `collect_report` requires a `manifest.json` that only `emit_jobs` writes, so the mismatch is not reachable today — but the two execution paths in this slice record their outcomes in entirely different ways.

`failure_breakdown` (`:249`) has a filter that silently disables it for the commonest sweep shape:

```
265	    axes = [k for k, vs in valuesets.items() if 1 < len(vs) < n]
```

For a one-dimensional sweep of N values over N runs, the swept key has exactly `n` distinct values, so `len(vs) < n` is false and the **only** axis is excluded. The function then prints just the return-code line — and its own header, "Failed runs by parameter (look for a regime, not just indices)", promises the per-parameter view it just dropped.

`ProgressBar._print_progress` computes `rate = self.completed / elapsed.total_seconds()` (`:412`) with no zero guard, while the parallel `SweepProgress.eta` (`:61-69`) does guard `elapsed_seconds == 0`. `SweepProgress` itself has **zero references** anywhere in the three files (not even the self-test at `:631`) — a dead-code candidate that duplicates `ProgressBar`'s counters. Flagging only, per project rule; `run.py` may import it and I cannot check.

`read_sweep_param` (`sweep_parser.py:262`) likewise has zero in-slice callers and is a near-duplicate of `read_sweep_config` (`:354`) minus tuple support and minus the tuple/sweep overlap check (`:462-468`). Handed a tuple file, it does not error — `"tuple(sfe, mCloud)    [0.01, 1e5] [0.10, 1e7]".split(None, 1)` gives `['tuple(sfe,', 'mCloud)    [0.01, 1e5] [0.10, 1e7]']`, a valid `key value` pair, so the tuple line becomes a base parameter named `tuple(sfe,` and the tuple axis vanishes silently.

## 9. Units: a negative result

`_validate_sweep_combination` converts `nCore` and `nISM` via `convert2au('cm**-3')` and `mu_convert` via `convert2au('m_H')` (`sweep_runner.py:113-121`) but passes `mCloud` and `rCloud_max` through unconverted (`:120`, `:127`). Given the internal system is `[Msun, pc, Myr]` (pinned via the shared exception), a mass in Msun and a radius in pc need no conversion, so this asymmetry is **correct**, not a bug.

Same conclusion for the physics table: `v2` is multiplied by `INV_CONV.v_au2kms` (`:543`, `:559`) because internal velocity is pc/Myr, while `t` and `R2` are printed raw under `t[Myr]` / `R2[pc]` headers (`:584-586`) — also correct, since those *are* the internal units. The only residual defect there is the silent `except Exception: v_to_kms = None` fallback (`:545-546`), which leaves the `[km/s]` header in place while printing pc/Myr, a ~2.3% discrepancy with no indication.
